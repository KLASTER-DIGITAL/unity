
# UNITY — Гайд для AI‑агента по планированию работ

Файл: `unity-ai-planner-guide.md`  
Версия: 1.0  
Дата: 2025‑11‑15  

Цель документа — дать **короткие и чёткие инструкции** AI‑агенту (Cursor / Lovable и т.п.), как:

1. Работать с текущей документацией и кодовой базой UNITY при ограничении по токенам.  
2. Находить устаревшие документы, архивировать их и оставлять только актуальные.  
3. На основе найденного строить **план работ по приоритетам** (backend, frontend, Supabase, AI, дизайн).

Документ — это «над‑слой» над всеми деталями в:

- `PROJECT_CONCEPT_AND_VALUE.md`, `UNITY_VISION_AND_ROADMAP_2026_v2.md`;
- `MOTIVATION_CARDS_SYSTEM.md`, `PUSH_SYSTEM.md`;
- `cards-and-push-tech.md`, `cards-and-push-scenarios.md`, `ai-prompts-cards.md`;
- `ACHIEVEMENTS_SYSTEM.md`, `REPORTS_SYSTEM.md`;
- `achievements-and-reports.md`, `achievements-review-and-plan.md`, `reports-review-and-plan.md`;
- `ai-superadmin-settings.md`, `ai-pdf-books.md`, `offline-prd.md`;
- других `.md` / `.ts` / Supabase миграциях.

---

## 1. Общие принципы работы агента

1. **Не загружать всю документацию сразу.**  
   - Работать по модулям: *Cards & Push → Achievements → Reports → AI Admin → Widgets*.
   - Для каждого модуля сначала читать «обзорные» файлы (`*-review-and-plan.md`, `*-tech.md`, `*-scenarios.md`), а потом — низкоуровневые.

2. **Всегда сверять документацию с реальной реализацией.**  
   - Проверять Supabase схемы, edge‑функции, React/PWA/React‑Native компоненты.  
   - Фиксировать расхождения: «описано в доке, но нет в коде» и наоборот.

3. **Отдавать приоритет более новым и агрегирующим документам.**  
   - Если есть `ACHIEVEMENTS_SYSTEM.md` и `achievements-review-and-plan.md` — спецификацию уточнять по `*-review-and-plan`.  
   - Если документы противоречат друг другу, более новый `*-review-and-plan` считается **истиной**, а старый переносится в архив.

4. **Строить план от фундамента к UX.**  
   Порядок:
   1. Данные и Supabase (таблицы, индексы, миграции).
   2. Edge Functions / API.
   3. AI‑операции и промпты (связь с `ai_operations` и SuperAdmin).
   4. PWA/React‑Native UI.
   5. Виджеты / PDF / продвинутый UX.

## 2. Шаг 1 — Инвентаризация документации и кода

### 2.1. Найти и сгруппировать документы

**Действия агента:**

1. Пройти по корню репозитория и папкам `/docs`, `/specs`, `/supabase`, `/apps/*/docs`.  
2. Построить таблицу вида:

   - `module` — cards, push, achievements, reports, ai-admin, pdf-books, offline, onboarding, widgets, misc;
   - `file` — имя файла;
   - `version/date` — если есть в шапке;
   - `type` — `concept`, `tech`, `review-and-plan`, `prd`, `old-spec`;
   - `status` — (определится далее как `active` или `archive`).

3. Сохранить эту таблицу в отдельный файл: `docs-index.md` или `docs-index.json`.

**Критерии:**

- Файлы с суффиксами `*-review-and-plan.md`, `*-tech.md`, `*-scenarios.md`, `ai-superadmin-settings.md`, `achievements-and-reports.md`, `cards-and-push-*.md`, `reports-review-and-plan.md` считать **кандидатами в основную актуальную документацию**.
- Старые спецификации (`*_SYSTEM.md`, старые PRD, черновики без версии/даты) считать как **поддерживающие / устаревающие**.

### 2.2. Быстрая проверка Supabase и кода

Для каждого модуля агент должен:

1. Найти соответствующие миграции Supabase:  
   - таблицы: `entries`, `entry_summaries`, `motivation_cards`, `push_subscriptions`,  
     `ai_operations`, `user_achievements`, `user_stats_daily`, `user_stats_monthly`, `user_reports` и пр.
2. Найти основной код:
   - Edge‑функции (`supabase/functions/**`);
   - экраны PWA и React Native (`HomeScreen`, `MotivationCardsSection`, `AchievementsScreen`, `ReportsScreen`, `Settings/AI` и т.д.).

3. Для каждого найденного модуля поставить статус:
   - `implemented` — реализовано и используется;
   - `partial` — реализовано частично / не совпадает с докой;
   - `missing` — в доке есть, в коде/БД нет.

Результат фиксируется в файле `implementation-status.md`.

## 3. Шаг 2 — Работа с устаревшей документацией

### 3.1. Правила, что считать устаревшим

Документ считается **устаревшим** и подлежащим архиву, если выполняется хотя бы одно:

1. Есть более новый документ по этому же модулю с пометкой `Версия`/датой позднее.  
2. Файл противоречит `*-review-and-plan.md` и/или `ai-superadmin-settings.md`.  
3. Описывает архитектуру, которая уже не отражена в текущей Supabase схеме и коде (по результатам шага 2.2).  
4. Это черновик / заметки без чёткой структуры (много текста, нет заголовка, версии).

### 3.2. Как архивировать

Агент должен:

1. Создать папку `/docs/archive` (если её нет).  
2. Для каждого устаревшего файла:
   - переместить файл в `/docs/archive` **или**  
   - добавить в шапку файла жирную строку:

     ```md
     > ⚠️ ARCHIVED: документ устарел, см. актуальную версию в `<имя нового файла>`.
     ```

3. Обновить `docs-index`:
   - для этих файлов выставить `status = archive`;
   - для актуальных — `status = active`.

### 3.3. Что оставить активным (минимальный набор)

Агент должен стремиться к тому, чтобы по каждому модулю был **1–2 основных файла**:

- **Карточки и Push:**
  - `cards-and-push-tech.md`
  - `cards-and-push-scenarios.md`
  - `ai-prompts-cards.md` (как либрари промптов)

- **Достижения и отчёты:**
  - `achievements-and-reports.md`
  - `achievements-review-and-plan.md`
  - `reports-review-and-plan.md`

- **AI‑админка и операции:**
  - `ai-superadmin-settings.md`

- **PDF-книги и оффлайн:**
  - `ai-pdf-books.md`
  - `offline-prd.md`

Все старые `*_SYSTEM.md` остаются как техническая детализация / история, но помечаются как `archive`, если противоречат новым планам.

## 4. Шаг 3 — Как составлять план работ (приоритеты)

### 4.1. Общий фрейм приоритизации

Агент должен строить план по следующим уровням приоритета:

1. **P0 — Надёжность и единый центр управления AI.**  
   Всё, что влияет на работоспособность карточек, пушей и бюджета AI.
2. **P1 — Повседневная ценность для пользователя.**  
   Карточки, push, прогресс/достижения → чтобы дневник реально помогал каждый день.
3. **P2 — Макро‑аналитика и отчёты.**  
   Недельные/месячные отчёты, связка с PDF‑книгами.
4. **P3 — Виджеты и продвинутый UX.**  
   Главный экран с виджетами, OS‑виджеты, анимации и т.п.

### 4.2. Детализация по уровням

#### P0 — AI Control Center и инфраструктура

**Цель:** всё AI‑и push‑ядро работает стабильно, управляется из супер‑админки, нет «магии в коде».

Агент должен:

1. Убедиться, что таблица `ai_operations` реализована и используется для:
   - `entry_analysis`;
   - `card_from_entry`;
   - `progress_card`;
   - `push_text`;
   - (в дальнейшем) `weekly_report`, `monthly_report`.
2. Синхронизировать UI «Назначение моделей» в супер‑админе с `ai-superadmin-settings.md`:
   - модели, лимиты, температуры берутся **из** `ai_operations`;
   - промпты редактируются в UI.
3. Проверить инфраструктуру push:
   - наличие и корректность VAPID‑ключей;
   - наличие `push_subscriptions`, webhooks, cron‑jobs;
   - корректную работу service worker.
4. Обновить документацию, чтобы P0‑состояние стало «истиной» (при необходимости скорректировать `cards-and-push-tech.md`).

#### P1 — Cards, Push, Achievements (ежедневная ценность)

**Цель:** пользователь каждый день получает **1–3 осмысленные карточки**, видит прогресс и получает понятные push.

Агент должен:

1. Синхронизировать текущую реализацию карточек с `cards-and-push-tech.md` и `cards-and-push-scenarios.md`:
   - окно 24 часа;
   - ограничение 1–3 карточки за заход;
   - поддержка типов `celebrate / reflect / focus / gratitude / progress`.
2. Проверить, что AI-промпты используются из `ai-prompts-cards.md`, а не из «жёстко захардкоженных» строк.
3. Для Achievements:
   - проверить наличие и состояние таблиц `achievements_catalog` и `user_achievements`;
   - если их нет — создать миграции **как минимум в упрощённом виде**;
   - связать флаг `is_achievement` из `entries` с начислением достижений.
4. Обновить экран «Достижения» по плану из `achievements-review-and-plan.md`:
   - лента достижений;
   - прогресс/серия (в UI слово «Прогресс», не «streak»);
   - базовый дашборд.

#### P2 — Отчёты, статистика и книги

**Цель:** у пользователя есть недельные/месячные обзоры и возможность собрать PDF‑книгу.

Агент должен:

1. Реализовать server‑side статистику (таблицы `user_stats_daily`, `user_stats_monthly`) по `reports-review-and-plan.md` и скорректировать `statsCalculator`.
2. Создать таблицу `user_reports` и базовые edge‑функции/handlers:
   - `GET /reports?period=week|month`;
   - `POST /reports/generate`.
3. Подключить AI‑операции `weekly_report` и `monthly_report` в `ai_operations` и супер‑админке.
4. Связать отчёты с PDF‑книгами (минимальный сценарий: месячный отчёт → PDF через текущий PDF‑пайплайн).

#### P3 — Главная, виджеты и OS‑виджеты

**Цель:** современный «рабочий стол» UNITY в стиле приложений из референсов.

Агент должен:

1. На основе `achievements-and-reports.md` и референсов дизайна:
   - спланировать набор виджетов на главной (прогресс дня, челлендж дня, фокус недели, настроение и т.д.);
   - описать их как отдельный документ `home-widgets-spec.md`.
2. Проверить, что API для быстрых OS‑виджетов может опираться на `user_stats_daily`, `user_stats_monthly` и `user_reports`.
3. Вынести задачи по UI в отдельный список (для дизайнера/фронтендера).

## 5. Что агент должен делать **после** формирования плана

После шагов 1–3 агент должен:

1. Сформировать файл `unity-roadmap-tasks.md`, где:
   - разделы P0 / P1 / P2 / P3;
   - под каждым — список задач в формате:
     - `[BE]`, `[FE]`, `[DB]`, `[AI]`, `[DOC]`;
     - краткое описание;
     - ссылки на соответствующие документы.
2. Для каждой задачи указать:
   - зависимость (например: «P1‑Ach‑3 зависит от P0‑AI‑2»);
   - примерный статус (если что‑то уже частично реализовано).
3. Использовать этот roadmap как главный вход в дальнейшей работе:
   - при старте новой сессии агент должен **сначала** открывать `unity-ai-planner-guide.md` и `unity-roadmap-tasks.md`,
   - выбирать ближайшую по приоритету незавершённую задачу,
   - только затем детально читать нужный модульный документ.

## 6. Рекомендуемый следующий шаг (для текущего состояния проекта)

С учётом существующей документации и фокуса UNITY, **следующая логичная итерация**:

1. **Забетонировать P0:**
   - привести в порядок `ai_operations` и UI AI‑настроек;
   - проверить VAPID, webhooks, cron и базовую доставку push.
2. **Сделать понятный MVP P1:**
   - карточки и push работают по новой логике (1–3 карточки, утро/вечер, доп. рекомендации);
   - раздел «Достижения» показывает реальный прогресс (с флагом `is_achievement` и базовыми достижениями).
3. **Подготовить основу для Weekly/Monthly отчётов:**
   - создать `user_stats_daily` и `user_stats_monthly` + простейший API;
   - пока даже без AI‑текстов — просто стат‑карточки в стиле референсов.

Этот гайд должен использоваться как **стартовая точка**: агент не переписывает его, а опирается на него при анализе, чтобы не тратить токены на чтение всего подряд и не теряться в версиях документов.
